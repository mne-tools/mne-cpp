# MNE-CPP v2.4.0 - Quality, Evidence, Parity

Release target: v2.4.0
Working theme: **Quality, Evidence, Parity**
Branch: `staging` (all work happens on `staging`; `main` is reserved for releases)
Target date: **Gate-driven; set after Milestone A measures the current baseline**

Last updated: 10 July 2026 - Replanned from the post-v2.3.0 baseline. The deferred feature list remains relevant, but it no longer controls the release. v2.4.0 is quality-first: testing, executable documentation, example coverage, reproducible screenshots, maintainability, and evidence-based MNE-Python parity are release work, not follow-up cleanup.

---

## Executive Intent

v2.4.0 should make MNE-CPP easier to trust, understand, extend, and compare. A public API is not complete merely because it compiles. It is complete when its behavior is tested, its provenance and parity status are recorded, a user can find and run an example, and the same example is represented in the generated API documentation.

The release has four ordered goals:

1. **Make quality measurable and blocking.** Tests, coverage, documentation, examples, screenshots, and static checks must have explicit CI gates and published reports.
2. **Turn examples into executable API documentation.** Adopt Skigen's Doxygen `@snippet` pattern, compile the source examples, execute deterministic examples, and generate API pages from those same sources.
3. **Measure and close MNE-Python parity with evidence.** Replace broad percentage claims with a versioned, machine-readable parity inventory and cross-validation tests.
4. **Deliver focused parity and strategic features.** Continue toward MNE-Python parity or exceed it in MNE-CPP's strengths: real-time operation, multimodal visualization, portable C++ deployment, and MNA workflows.

Quality gates take priority over feature count. If a feature threatens the release gates, the feature moves; the gates do not.

## Multi-Agent Execution Model

v2.2.0 worked best when tasks named concrete files, APIs, tests, and acceptance criteria. v2.3.0 improved tracking with hierarchical sub-task IDs and test counts. v2.4.0 combines both patterns while avoiding duplicated status narratives: the sub-task tables below are the canonical source of implementation status.

### Status vocabulary

Use only these values in sub-task tables:

- **Planned** - specified and ready for prerequisite work.
- **Ready** - all dependencies satisfied; safe to assign.
- **In progress** - one named agent owns the package.
- **Blocked** - blocker and owner recorded in Notes.
- **Review** - implementation complete; acceptance checks pending/reviewing.
- **Done** - all acceptance IDs pass and evidence is linked.
- **Deferred** - explicitly removed from v2.4 scope with rationale.
- **Candidate** - an option awaiting T8.0 scope promotion; do not assign an implementation agent until it becomes Ready.

Do not copy completion narratives into multiple sections. Update the canonical sub-task row, commit/test evidence, and the aggregate TASK row only.

### Active assignment ledger

Only packages in **In progress** or **Review** appear here. Remove the row when the canonical package status becomes Done, Blocked, or Deferred.

| Package ID | Agent | Branch/worktree | Started | Handoff / PR |
|------------|-------|-----------------|---------|--------------|
| _None_ | - | - | - | - |

### Agent work-package contract

Every agent assignment must include this handoff block:

```text
Package ID: T<task>.<subtask>[letter]
Assigned agent: Agent name/role.
Branch/worktree: Isolated implementation location.
Goal: One independently testable outcome.
Own paths: Files/directories the agent may edit.
Read-only dependencies: Nearby interfaces the agent may inspect but not refactor.
Do not edit: Shared hotspots reserved for an integration package.
Depends on: Required completed package IDs.
Can run with: Known conflict-free package IDs.
Deliverables: Code, tests, docs, generated metadata, or reports.
Validation: Exact focused commands/checks to run.
Acceptance IDs: AC-T<task>.<subtask>-<n>.
Handoff: Changed files, commands/results, risks, and follow-up items.
```

Only IDs appearing in canonical package-table rows are assignable. `T7.6` and `T9.1`-`T9.5` are organizational parent-tree labels; agents receive leaf IDs such as `T7.6a` or `T9.3c`.

An agent must not broaden its path ownership because a nearby cleanup is convenient. New shared-file needs are handed to the wave's integration agent.

### Integration policy

1. One agent owns one package at a time; one package produces one reviewable change set.
2. Leaf work lands before shared integration work. Integration agents do not rewrite leaf implementations.
3. Characterization tests land before behavior-preserving maintainability refactors.
4. Schema changes land before registry/example migrations that consume them.
5. Generated files are produced once by the integration package after all source inputs land.
6. Every package runs focused validation; the integration package runs the task-level suite; the milestone owner runs the gate-level suite.
7. A package is not Done when code is written; it is Done when its acceptance IDs and artifacts are recorded.

## Non-Negotiable Release Gates

Numeric coverage thresholds below are proposed v2.4.0 minimums. TASK 0 records the fresh baseline and cost. Any threshold change after that checkpoint requires an explicit decision in this document; it must not be silently weakened in workflow YAML.

### G1 - Test Integrity

- 100% of built `test_*` executables appear in `ctest -N`; the build fails on unregistered tests.
- CI runs CTest on Ubuntu, macOS, and Windows and publishes JUnit results.
- No automatic retry converts a failure into success. A flaky test must fail, be fixed, or enter a named quarantine with owner, issue, and expiry date.
- Tests use labels (`unit`, `integration`, `parity`, `example`, `gui`, `slow`, `requires-data`) and documented timeouts.
- The full Linux suite runs against both the minimum and maximum supported Qt versions; the other platforms run the release Qt version.
- Release candidate: zero failures, zero expired quarantines, and zero tests skipped without a documented platform/data reason.

### G2 - High and Non-Regressing Coverage

- Generate a current line and branch coverage baseline split into libraries, applications, and tools.
- Release minimums: libraries >= 70% line / 55% branch; applications and tools each >= 50% line; combined release scope >= 60% line.
- New or materially changed production code: >= 90% line coverage and meaningful branch/error-path tests.
- Codecov patch coverage >= 90%; project coverage may not decrease by more than 0.1 percentage point.
- No public algorithm is considered parity-complete without normal, boundary, invalid-input, and numerical-reference coverage.
- Repair the local coverage baseline cache and enforce the same configured threshold that the workflow advertises.
- `[skip-coverage]` is forbidden on release-candidate and release commits.
- Publish and retain the v2.4.0 coverage report with per-module trends and an explicit exclusion list.

### G3 - Complete, Executable API Documentation

- 100% of exported public classes/functions are present in Doxygen XML and in `doc/api_registry.json`, or carry an explicit, reviewed exclusion.
- Run Doxygen, registry/XML drift audit, `doxy2mdx.py --strict`, generated-file diff check, and Docusaurus build in PR, staging, and main CI.
- Doxygen documentation errors, missing parameter/return documentation, broken links, broken images, and orphan registry entries are fatal.
- Every new or changed public API has API documentation, provenance, a test, and an executable example before merge.
- Every example-eligible existing API has an example by release. Non-eligible records require `example_exempt` and a reason; coverage is reported as eligible-backed/eligible-total rather than hidden by exemptions.
- Release gate: 100% example coverage among eligible APIs and 100% for all new/changed public APIs.

### G4 - Generated Screenshots and Visual Evidence

- CI builds and runs `mne_doc_shots`; 1x1 placeholders are removed from all website workflows.
- Every entry in `doc/website/screenshots/manifest.json` is generated from a deterministic scenario before the website build.
- Validate PNG decoding, expected dimensions, non-zero size, and nonblank pixel variance.
- Generated documentation pages reference those outputs automatically; the website build must not depend on manually captured local images.
- Linux provides canonical documentation images. Linux and macOS run visual smoke/regression coverage for supported rendering paths.
- `mne_screenshot_regression` either receives committed/versioned golden references with normalized RMSE <= 0.01 or is renamed to an explicit smoke test. A regression job must perform a comparison.
- Upload screenshots, diffs, and comparison metrics as CI artifacts on both success and failure.

### G5 - Maintainability and Static Quality

- No new compiler warnings on the supported compiler/Qt matrix; warning counts are published and must trend to zero.
- `clang-format --dry-run --Werror` is blocking for changed C/C++ files.
- Introduce a focused `clang-tidy` profile for changed code first, then ratchet verified modules into the blocking set.
- SPDX/license validation is strict and blocking on pull requests.
- CodeQL uses security-and-quality queries; no unresolved new high-severity CodeQL or Coverity findings.
- Refresh the optimization and gap inventories with dated, generated counts. Raw owning pointers, C-style casts, `NULL`, legacy `typedef struct`, `printf`, duplicated algorithms, and smoke-only tests must not increase.
- Prefer ownership types, const-correct APIs, scoped enums, structured logging, and smaller dependency boundaries in touched code. Broad mechanical cleanup must remain separately reviewable from behavior changes.

### G6 - Evidence-Based MNE-Python Parity

- Pin the MNE-Python reference release and all Python dependencies used to generate parity fixtures.
- Add a machine-readable MNE-Python API inventory that includes missing APIs, not only existing C++ classes.
- Each tracked item has a status: `missing`, `partial`, `equivalent`, `exceeds`, `not-applicable`, or `external`.
- `equivalent` requires a cross-validation test, documented tolerance/rationale, API documentation, and an executable example.
- `exceeds` requires the equivalent criteria plus a documented MNE-CPP capability beyond MNE-Python, such as real-time operation, native GUI integration, streaming, lower deployment footprint, or measured performance.
- CI reports parity by domain and status. No aggregate parity percentage is published without its inventory, denominator, reference version, and evidence links.
- Committed fixtures are regenerated by a pinned script; normal CI remains deterministic and does not depend on the latest PyPI packages.

### G7 - Trusted, Signed Release Artifacts

Downloaded installers must not be flagged as untrusted or dangerous by the operating system. Users should be able to install without SmartScreen/Gatekeeper "unidentified developer" or "unknown publisher" warnings.

- **Windows (required for v2.4.0):** the Windows installer and its bundled executables are Authenticode-signed and timestamped with a trusted timestamp authority. Windows signing must be enabled for the release because it can be obtained at no per-signature cost; the release is not signable-optional on Windows.
- **macOS (required if signing/notarization credentials are available):** the `.app` and `.dmg` are signed with a Developer ID Application certificate, use the hardened runtime, and are notarized and stapled with `notarytool`. This depends on a paid Apple Developer Program membership; when the certificate/notary profile is present the release must be signed and notarized, and when absent the limitation must be explicitly recorded in the release notes rather than silently shipping unsigned.
- **Linux:** provide verifiable integrity via published SHA-256 checksums for every artifact; an optional detached GPG signature may be added if a maintainer key is available.
- Signing secrets/certificates are never committed; they are consumed only from CI secrets and never printed to logs.
- Every release artifact has a published checksum, and signature/notarization status is recorded in the release evidence bundle and release notes.
- Signing is verified in CI after packaging: `signtool verify` on Windows and `codesign --verify` plus `spctl`/notarization checks on macOS.

## Delivery Order and Scope Control

### Milestone A - Measure and Repair the Foundation

TASK 0, CTest migration, current coverage report, workflow threshold/cache fixes, strict API pipeline skeleton, and real screenshot generation.

**Exit:** Baselines are reproducible; no test is invisible; documentation and screenshot jobs run on pull requests.

### Milestone B - Make Quality Blocking

TASKs 1-6: labels/JUnit, coverage ratchets, named snippets, registry validation, strict docs, screenshot audit/goldens, and changed-code maintainability gates.

**Exit:** G1-G5 are operational. New APIs cannot merge without tests, examples, and documentation.

### Milestone C - Establish Parity Evidence

TASK 7 and the first high-impact TASK 8 slices. Pin MNE-Python, publish the complete inventory, convert priority comparisons to deterministic fixtures, and identify genuine exceed areas.

**Exit:** G6 is operational and the v2.4 parity scope is frozen from evidence rather than estimates.

### Milestone D - Focused Feature Delivery

Complete selected TASK 8 parity items and TASK 9 strategic features through the shared Definition of Done.

**Exit:** All selected functionality is tested, example-backed, documented, and represented in quality/parity reports.

### Milestone E - Release Candidate

Feature freeze; run the complete matrix and evidence bundle; burn down coverage, documentation, visual, static-analysis, parity, and signing gaps only.

**Exit:** G1-G7 pass without release-only exceptions.

Scope rules:

- P0 quality infrastructure and release gates precede P1 feature expansion.
- At least half of v2.4 engineering capacity remains allocated to quality, tests, examples, documentation, and maintainability until Milestone B exits.
- No new public API may increase test/example/documentation debt.
- A candidate feature without its test/example/docs plan remains backlog, regardless of implementation progress.
- P2 scope begins only after the release gates are on track.
